# Pinpoint Review 아키텍처 정의서

MariaDB / FastAPI 기준 · 프로젝트 기초 구조 충족 여부와 주요 개선점 중심

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 프로젝트 | Pinpoint (Pinpoint Review) |
| 목표 사용자 | 네이버 스마트스토어·쿠팡 등 중소형 셀러, 자사몰 운영자 (서비스 이용자 = 쇼핑몰 운영자, 셀러와 CS 담당자를 USERS 하나로 통합) |
| 핵심 가치 | 리뷰 텍스트에서 긍/부정 키워드를 자동 추출하고, 상품 문제와 유통·포장 문제를 분리해 CS 대응 속도를 높이고 제품 개선 가이드를 제공 |
| 범위 | 리뷰 수집·정제·분석, 상품별 리뷰 조회, 악성 리뷰 블라인드(US-06), CS 답글(CS챗봇), 통계 대시보드·쇼핑몰 분석, CSV 내보내기, 위험 키워드 관리. LLM 사과문 추천과 경쟁 상품 비교는 Could (답글 추천은 규칙 기반 템플릿, 상품 비교는 `/compare` 화면으로 구현. LLM 연동은 이번 범위에서 제외) |

## 2. 시스템 구성

```
[브라우저] --HTML 폼 / 페이지 요청--> [FastAPI 화면 라우트 main.py] --Jinja2 템플릿--> HTML
    |                                         |
    +--fetch (차트 데이터), 세션 쿠키--> [FastAPI REST API api_v1.py /api/v1]
                                              |
                                              +--SQLAlchemy--> [MariaDB]
                                              +--(이번 범위 제외) LLM API: 분석 리포트·사과문 초안

[내부 파이프라인 /api/v1/internal/*]  데이터셋 -> 적재 -> 텍스트 클리닝 -> 감성/위험도/이슈유형/키워드 분석 -> MariaDB
```

| 계층 | 기술 | 책임 |
| --- | --- | --- |
| 화면 | Jinja2 템플릿(서버에서 HTML 생성, `backend/templates`) + JavaScript fetch + ECharts | 로그인, 폼 처리, 리뷰 목록·블라인드, CS챗봇, 통계 차트(fetch 로 `/api/v1/stats/*` 호출) |
| 디자인 시안 | 정적 HTML (`frontend/`) | 디자이너 작업본. 서버에서는 사용하지 않고 템플릿에 반영 |
| API 서버 | FastAPI, Pydantic v2, SQLAlchemy 2.0 | 인증·인가, 리뷰·답글·통계 API, 입력 검증. 테이블은 서버 시작 시 자동 생성 (Alembic 마이그레이션은 미사용) |
| 데이터베이스 | MariaDB 10.5+ (utf8mb4), 임베딩은 JSON 컬럼 | 15개 테이블 (`04_database_design.md`) |
| 데이터·AI 파이프라인 | 규칙 기반 분석 (`analysis.py`, `rule-v2`) | 적재, 정제, 감성·위험도·이슈유형·키워드 라벨링. 감성 모델·LLM 은 `analyze_review()` 교체로 도입 예정 |
| 실행 환경 | 로컬 (uvicorn, 프로세스 1개) | 배포 절차는 `10_deployment.md`. 시도 제한 기록이 서버 메모리에 있으므로 `--workers` 는 1 로 실행 |

## 3. 핵심 설계 결정

| # | 결정 | 내용 |
| --- | --- | --- |
| D1 | 리뷰는 수집 데이터 | 사용자가 리뷰를 작성·수정하지 않는다. US-06은 "셀러가 근거 없는 악성 리뷰를 블라인드"로 변경 |
| D2 | 블라인드는 소프트 삭제 | 물리 삭제 없이 `reviews.status = BLINDED`, `blind_reason` 필수, 이력은 `review_blind_logs`에 기록 |
| D3 | 소유권 기반 인가 | 역할(role) 없이 `products.seller_id = 요청자` 여부로만 판단, 아니면 403 |
| D4 | 답글 정책 | 블라인드된 리뷰에는 답글 등록 불가(409). 상위 답글 삭제 시 하위 답글도 함께 삭제(`ON DELETE CASCADE`) |
| D5 | 탈퇴 정책 | 하드 삭제: `users` 행을 지우고 연결 데이터는 외래키 `CASCADE` 로 함께 삭제, 서비스 의견(`feedbacks`)만 작성자 NULL 로 남김. 재가입 허용 (`auth.delete_account`) |
| D6 | 임베딩 저장 | MariaDB JSON 컬럼. 벡터 인덱스를 쓸 수 없어 유사도는 애플리케이션(NumPy)에서 계산 |

## 4. 인증·인가

| 항목 | 방식 |
| --- | --- |
| 인증 | 이메일·비밀번호 로그인 후 세션 생성, 세션 쿠키(HttpOnly, Secure, SameSite=Lax) 발급. 화면과 REST API 가 같은 세션 쿠키를 사용. FastAPI가 HTML을 같은 출처로 제공하므로 CORS 설정 불필요. 비밀번호는 단방향 해시(PBKDF2-SHA256, 솔트 포함) 저장 |
| 로그아웃 | 서버가 세션 행을 삭제하고 쿠키를 만료시켜 즉시 무효화. 만료된 세션은 sessions.expires_at 기준으로 정리 |
| 인가 | 모든 리소스(상품, 리뷰, 답글, 위험 키워드)를 본인 상품 기준으로만 접근. 위반 시 API 는 403, 화면은 404(존재 여부를 노출하지 않음) |
| 답글 수정·삭제 | 작성자 본인만 가능 |
| 이메일 인증 | 회원가입(화면·API)·비밀번호 변경 시 6자리 코드 메일 발송 (`email_verify.py`). 코드의 HMAC 해시·만료·틀린 횟수는 **서버 메모리에만** 저장 (브라우저 쿠키에는 없음). 10분 유효, 1회용, 재발송 60초, 5회 오류 시 폐기, 발송은 이메일당 1시간 5회·IP당 20회. DB 변경 없음. `MAIL_HOST` 가 없으면 개발 모드로 화면에 코드 표시 |
| 로그인 시도 제한 | 같은 이메일 5회 실패 → 10분 잠금, 같은 IP 20회 실패 → 10분 잠금. 화면(`/login`)과 API(`/auth/login`, 429 `LOGIN_LOCKED`)가 같은 기록 사용. 로그인 성공·비밀번호 변경 시 해제 (`rate_limit.py`) |
| 비밀번호 변경(찾기) | 이름·이메일(인증 코드)·사업자 등록번호 일치 시 변경, 5회 불일치 시 10분 잠금(이메일·IP 기준, 서버 기록), 변경 후 모든 세션 삭제 |
| 서명 키 | 화면 안내 메시지 쿠키(`pp_flash`)는 `SECRET_KEY` 로 서명. 비었거나 예시 값이면 서버 시작 시 경고 |
| 운영 모드 | `COOKIE_SECURE=1` 이면 운영으로 보고, 메일 서버가 없어도 인증 코드를 화면에 보여 주지 않음 (503 + 시작 시 경고). 화면 코드 표시는 로컬 개발에서만 |
| 제한 값 설정 | 로그인·인증 메일 제한 횟수는 `.env` 로 조정 (`LOGIN_MAX_FAILS`, `LOGIN_LOCK_MINUTES`, `LOGIN_IP_MAX_FAILS`, `EMAIL_SEND_LIMIT_PER_EMAIL`, `EMAIL_SEND_LIMIT_PER_IP`) |
| CSV 내보내기 | `=`, `+`, `-`, `@` 로 시작하는 칸은 앞에 `'` 를 붙여 엑셀 수식 실행 방지 (`api_v1.csv_safe`) |
| 내부 API(`/internal/*`) | 관리자 role이 없으므로 로그인 세션이 아닌 API 키(`X-Internal-Key` 헤더 = `.env` 의 `INTERNAL_API_KEY`)로만 허용 |

**시도 제한의 한계:** 기록이 서버 프로세스 메모리에 있으므로 서버를 재시작하면 초기화되고, 여러 프로세스로 실행하면 프로세스마다 따로 셉니다. 이 프로젝트는 프로세스 1개로 운영하며, 규모가 커지면 Redis 같은 공유 저장소로 옮깁니다. 프록시(nginx) 뒤에 배포할 때는 실제 사용자 IP 를 받도록 `uvicorn --proxy-headers` 를 사용합니다 (`10_deployment.md`).

처리 순서는 요청 → 세션 쿠키 확인 → 세션 조회·만료 확인 → 대상 리소스 조회(404) → 소유권 확인(403) → 상태 확인(예: 블라인드 리뷰, 409) → 처리입니다.

## 5. 주요 데이터 흐름

**수집·분석 (배치):** 데이터셋 다운로드 → 중복·결측 처리와 ingest_logs 기록 → content_raw(원문)와 content_clean(정제본) 분리 저장 → 감성·키워드·이슈유형 분석 결과를 review_analysis, keywords, review_keywords에 저장

**CSV 업로드 검증:** 필수값(상품명·평점·리뷰내용·작성일), 평점 1~5 정수, 작성일은 오늘 이전, 상품명 255자·본문 65,535바이트 이하. 어긋난 행은 잘라 저장하지 않고 행 번호와 이유를 안내한 뒤 건너뜀 (`pipeline._row_problem`, 8일차 Agent Task T-8-1)

**대시보드 조회:** 필터(상품, 기간) → 통계 API가 status = 'VISIBLE' 리뷰만 집계 → 월별 추이, 긍/부정 비율, 키워드 TOP 10, 위험 리뷰(최신순·심각도순) 응답

**블라인드:** 상품별 대시보드에서 사유 입력(필수) → 소유권 확인 → status, blind_reason, blinded_by, blinded_at 갱신과 이력 기록 → 이후 통계에서 제외. '블라인드된 리뷰' 목록에서 복구 가능

**CS챗봇:** 답글 없는 리뷰를 위험도순으로 표시 → 추천 답글(템플릿) 수정·복사 → 쇼핑몰에 붙여넣기 → '처리 완료' 시 최종 답글을 review_replies 에 저장 → 목록에서 제외 (되돌리기 가능)

**감성 분류 (`rule-v2`):** 평점 4~5점이고 위험 키워드가 없으면 긍정, 위험 키워드가 없는 3점이면 중립, 그 외(1~2점 또는 위험 키워드 포함)는 부정. 이슈 유형(상품·배송·포장·기타)은 부정 리뷰에만 붙고, 중립 리뷰는 키워드 TOP 10 집계에서 제외

**위험 키워드:** 설정 화면·API 에서 추가·수정·삭제하면 그 단어가 들어간 기존 리뷰를 즉시 재분석해 반영 ('전체 리뷰 다시 분석'은 전체 재분석용)

## 7. 주요 개선점과 반영 결과

| 우선순위 | 개선점 | 결과 |
| --- | --- | --- |
| 1 | 블라인드(소프트 삭제) 정책 통일 | 반영: `status` (`VISIBLE`/`BLINDED`) 사용, 통계·위험 리뷰·키워드·CSV 집계를 공통 조건 한 곳(`api_v1._scope`)에서 관리 |
| 2 | ERD와 API 필드 정합성 | 반영: JSON 키 snake_case, ID 정수(BIGINT) 통일 |
| 3 | 에러 응답 규격 정의 | 반영: `{code, message}` + 400/401/403/404/409/422/429 |
| 4 | UI 설계와 요구사항 동기화 | 반영: 블라인드 사유 입력·복구 화면, 예외 화면, CS챗봇·분석 화면 |
| 5 | 인증·인가를 아키텍처 문서에 명시 | 반영: 4장 (JWT 대신 세션·쿠키 방식으로 확정, `/internal/*` 은 API 키) |
| 6 | 분석 결과 재현성 | 반영: `review_analysis.model_version` 기록 (`rule-v2`). 규칙을 바꾸면 서버 시작 시 예전 버전 결과를 자동 재분석 (`database.reanalyze_outdated`) |
| 7 | 인증 시도 제한을 서버에서 관리 (7일차) | 반영: 인증 코드·로그인·비밀번호 찾기 실패 기록을 쿠키가 아닌 서버 메모리에 저장 (`rate_limit.py`). 쿠키 조작·삭제로 우회 불가 |
| 8 | 감성 3분류 (7일차) | 반영: 위험 키워드 없는 3점 리뷰를 중립(NEU)으로 분류. 긍/부정/중립 차트·상품 비교·CS챗봇에 표시 |

## 8. 미결정 사항

- ~~블라인드 복구 허용 여부~~ → 허용으로 결정 (화면·API 모두 복구 가능, 이력 기록)
- 감성 분석을 LLM API로만 처리할지, 공개 한국어 모델과 혼합할지 (이번 범위에서는 LLM 연동 제외로 결정, 규칙 기반 `rule-v2` 유지)
- 임베딩 사용처 (유사 리뷰 검색, 경쟁 상품 비교 등) 확정 전까지는 컬럼만 유지
- 상품 등록 API 필요 여부 (현재는 데이터셋 적재 전용 가정)
- 한 계정이 여러 쇼핑몰을 운영할 가능성 (현재 계정당 하나, 사업자번호 UNIQUE)
