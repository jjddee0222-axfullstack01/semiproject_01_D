# Pinpoint Review 아키텍처 정의서

MariaDB / FastAPI 기준 · 프로젝트 기초 구조 충족 여부와 주요 개선점 중심

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 프로젝트 | Pinpoint (Pinpoint Review) |
| 목표 사용자 | 네이버 스마트스토어·쿠팡 등 중소형 셀러, 자사몰 운영자 (서비스 이용자 = 쇼핑몰 운영자, 셀러와 CS 담당자를 USERS 하나로 통합) |
| 핵심 가치 | 리뷰 텍스트에서 긍/부정 키워드를 자동 추출하고, 상품 문제와 유통·포장 문제를 분리해 CS 대응 속도를 높이고 제품 개선 가이드를 제공 |
| 범위 | 리뷰 수집·정제·분석, 상품별 리뷰 조회, 악성 리뷰 블라인드(US-06), CS 답글, 통계 대시보드, CSV 내보내기. LLM 사과문 추천과 경쟁 상품 비교는 Could |

## 2. 시스템 구성

```
[React 대시보드] --REST/JSON, JWT--> [FastAPI]  --SQLAlchemy--> [MariaDB]
                                        |
                                        +--> [LLM API]  분석 보조, 사과문 초안

[배치 스크립트]  데이터셋 -> 적재 -> 텍스트 클리닝 -> 감성/키워드/이슈유형 분석 -> MariaDB
```

| 계층 | 기술 | 책임 |
| --- | --- | --- |
| 프론트엔드 | React + Vite + TypeScript, ECharts | 로그인, 필터, 차트, 리뷰 목록, 블라인드·답글 모달 |
| API 서버 | FastAPI, Pydantic v2, SQLAlchemy 2.0, Alembic | 인증·인가, 리뷰·답글·통계 API, 입력 검증 |
| 데이터베이스 | MariaDB 10.5+ (utf8mb4), 임베딩은 JSON 컬럼 | 12개 테이블 (USERS, PRODUCTS, REVIEWS, REVIEW\_ANALYSIS 등) |
| 데이터·AI 파이프라인 | pandas, kiwipiepy, 제공된 LLM API | 적재, 정제, 감성·키워드·이슈유형 라벨링 (새 모델은 학습하지 않음) |
| 실행 환경 | Docker Compose | FastAPI, MariaDB, 프론트 일괄 기동 |

## 3. 핵심 설계 결정

| # | 결정 | 내용 |
| --- | --- | --- |
| D1 | 리뷰는 수집 데이터 | 사용자가 리뷰를 작성·수정하지 않는다. US-06은 "셀러가 근거 없는 악성 리뷰를 블라인드"로 변경 |
| D2 | 블라인드는 소프트 삭제 | 물리 삭제 없이 `reviews.status = BLINDED`, `blind_reason` 필수, 이력은 `review_blind_logs`에 기록 |
| D3 | 소유권 기반 인가 | 역할(role) 없이 `products.seller_id = 요청자` 여부로만 판단, 아니면 403 |
| D4 | 답글 정책 | 블라인드된 리뷰에는 답글 등록 불가(409). 상위 답글 삭제 시 하위 답글도 함께 삭제(`ON DELETE CASCADE`) |
| D5 | 탈퇴 정책 | `users.status = WITHDRAWN`으로 소프트 처리, 답글 작성자·블라인드 처리자는 NULL로 익명화 |
| D6 | 임베딩 저장 | MariaDB JSON 컬럼. 벡터 인덱스를 쓸 수 없어 유사도는 애플리케이션(NumPy)에서 계산 |

## 4. 인증·인가

| 항목 | 방식 |
| --- | --- |
| 인증 | 이메일·비밀번호 로그인 후 JWT 발급. 비밀번호는 argon2 등 단방향 해시 저장 |
| 로그아웃 | JWT는 서버에서 만료시킬 수 없어 `token_blacklist`에 jti를 저장하고 요청마다 검사 |
| 인가 | 모든 리소스(상품, 리뷰, 답글, 위험 키워드)를 본인 상품 기준으로만 접근. 위반 시 403 |
| 답글 수정·삭제 | 작성자 본인만 가능 |
| 내부 API(`/internal/*`) | 관리자 role이 없으므로 일반 JWT가 아닌 서버 내부 호출 또는 API 키로만 허용 |

처리 순서는 요청 → JWT 검증 → 블랙리스트 확인 → 대상 리소스 조회(404) → 소유권 확인(403) → 상태 확인(예: 블라인드 리뷰, 409) → 처리입니다.

## 5. 주요 데이터 흐름

**수집·분석 (배치):** 데이터셋 다운로드 → 중복·결측 처리와 `ingest_logs` 기록 → `content_raw`(원문)와 `content_clean`(정제본) 분리 저장 → 감성·키워드·이슈유형 분석 결과를 `review_analysis`, `keywords`, `review_keywords`에 저장

**대시보드 조회:** 필터(상품, 기간) → 통계 API가 `status = 'VISIBLE'` 리뷰만 집계 → 월별 추이, 긍/부정 비율, 키워드 TOP 10, 위험 리뷰(최신순·심각도순) 응답

**블라인드:** 사유 입력(필수) → 소유권 확인 → `status`, `blind_reason`, `blinded_by`, `blinded_at` 갱신과 이력 기록 → 이후 통계에서 제외

## 7. 주요 개선점

| 우선순위 | 개선점 | 조치 |
| --- | --- | --- |
| 1 | **블라인드(소프트 삭제) 정책 통일** | 컬럼은 `is_deleted`가 아니라 `status` (`VISIBLE`/`BLINDED`)를 사용. 평균 평점, 월별 추이, 긍/부정 비율, 키워드 TOP 10, 위험 리뷰 목록, CSV 내보내기에 모두 `WHERE status = 'VISIBLE'`을 동일하게 적용하고, 블라인드 목록 조회에서만 예외 허용. 한 곳이라도 빠지면 평점이 왜곡되므로 공통 쿼리 조건(리포지토리 계층)으로 한 곳에서 관리 |
| 2 | **ERD와 API 필드 정합성** | 표기법 하나로 통일(권장: JSON 키도 DB와 같은 snake\_case, 카멜케이스가 필요하면 Pydantic alias로 변환). ID 타입은 DDL이 `BIGINT UNSIGNED AUTO_INCREMENT`이므로 API 경로·본문도 정수로 통일하고 UUID와 혼용하지 않음. `04_database_design.md`와 `05_api_spec.md`를 컬럼 단위로 1:1 대조 |
| 3 | **에러 응답 규격 정의** | 공통 오류 형식 하나(예: `{code, message}`)와 상태 코드 표를 명세에 추가: 400/422 입력 오류, 401 인증 실패, 403 권한 없음, 404 없음, 409 상태 충돌(이미 블라인드, 블라인드 리뷰에 답글). 현재 일부 API는 403·404 응답이 누락되어 있음 |
| 4 | **UI 설계와 요구사항 동기화** | US-06 변경으로 "리뷰 작성·수정·삭제 모달"은 불필요해지고 "블라인드 사유 입력 모달"과 "하위 답글까지 삭제된다는 확인 창"이 필요. 예외 화면(데이터 없음, 403, 404, 에러 페이지)과 블라인드 리뷰의 답글 입력 비활성 상태를 추가 |
| 5 | **인증·인가를 아키텍처 문서에 명시** | 4장의 JWT, 블랙리스트, 소유권 검사 순서를 `06_architecture.md`에 반영. 관리자 role이 없으므로 `/internal/*` 보호 방식 확정 |
| 6 | **분석 결과 재현성** | `review_analysis.model_version`을 기록해 모델·프롬프트 변경 시 재분석 범위를 식별 |

## 8. 미결정 사항

- 블라인드 복구 허용 여부 (현재 API 후보에는 복구가 있음)
- 감성 분석을 LLM API로만 처리할지, 공개 한국어 모델과 혼합할지 (데이터셋 규모에 따라 결정)
- 임베딩 사용처 (유사 리뷰 검색, 경쟁 상품 비교 등) 확정 전까지는 컬럼만 유지
- 상품 등록 API 필요 여부 (현재는 데이터셋 적재 전용 가정)
- 한 계정이 여러 쇼핑몰을 운영할 가능성 (현재 계정당 하나, 사업자번호 UNIQUE)
